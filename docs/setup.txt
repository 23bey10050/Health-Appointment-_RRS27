===============================================================================
HEALTH APPOINTMENT - SETUP GUIDE
===============================================================================

This is a plain text file rather than Markdown on purpose: the project owner
asked that no .md file be committed, and setup notes still have to travel with
the code. Everything below is the click-by-click path from an empty machine to
a running app.

-------------------------------------------------------------------------------
WHAT YOU NEED INSTALLED
-------------------------------------------------------------------------------

  Node.js 22 or newer     https://nodejs.org
  Docker Desktop          https://docker.com   (only for the local database)
  Git

Check them:

  node --version
  docker --version

-------------------------------------------------------------------------------
RUN IT LOCALLY (about two minutes, no online accounts needed)
-------------------------------------------------------------------------------

  1. Copy the environment template:

       cp .env.local .env

     On Windows PowerShell:  Copy-Item .env.local .env

     .env.local is committed and holds placeholders only. .env is yours and is
     never committed - that split is what keeps real keys off GitHub.

  2. Install dependencies (one command, it covers every workspace):

       npm install

  3. Start Postgres:

       npm run db:up

     This runs Postgres 16 in Docker on port 5432 with the exact username,
     password and database name the default DATABASE_URL expects, so step 1
     needs no editing to work.

     Watch it become ready:   npm run db:logs
     Stop it later:           npm run db:down

  4. Create the tables and fill in a demo clinic:

       npm run db:migrate
       npm run db:seed

     Both are safe to run twice. Migrations remember what has already been
     applied, and the seed skips anything that is already there.

  5. Start the API:

       npm run dev

  6. Confirm it is alive:

       curl http://localhost:4000/health
       curl http://localhost:4000/ready

     /health answers even when the database is down, on purpose. /ready is the
     one that tells you whether Postgres is actually reachable.

  7. In a second terminal, start the browser app:

       npm run dev:web

     Open http://localhost:5173 - that is the whole patient portal. Register a
     new account (always a patient, whatever the form is asked to send - the
     API itself enforces that) or sign in with one of the demo logins above,
     search for a doctor, hold a slot, fill in the symptom form, and the
     appointment is real: it is in Postgres, and if BREVO_API_KEY is not set,
     its confirmation email is sitting in the API's own terminal window.

     A seeded doctor account (mehta@clinic.test, password Clinic@2026) lands
     on their own daily schedule instead - open a booked appointment to see
     the pre-visit AI brief and, once notes are submitted, the completed
     visit's notes and prescription; "Days off" lets a doctor mark a leave
     day with a preview of how many booked patients it would affect before
     confirming. The seeded admin (admin@clinic.test, same password) lands
     on a dashboard with three sections: Doctors (create an account, edit a
     profile, manage shifts, mark days off for any doctor, deactivate and
     reactivate), Notification health (queued/sent/failed/dead-letter counts
     with one-click retry), and the Audit log (every recorded action,
     filterable by action or entity type).

-------------------------------------------------------------------------------
IF PORT 5432 IS ALREADY TAKEN
-------------------------------------------------------------------------------

Another Postgres is probably running on your machine. Either stop it, or edit
the ports line in docker-compose.yml to '5433:5432' and change the port in
DATABASE_URL inside your .env to match.

-------------------------------------------------------------------------------
TRYING THE AUTH ENDPOINTS
-------------------------------------------------------------------------------

  curl -X POST http://localhost:4000/auth/login \
    -H "Content-Type: application/json" \
    -d '{"email":"admin@clinic.test","password":"Clinic@2026"}'

Returns an access token (15 minutes) and a refresh token (30 days). Send the
access token on later requests as:

    Authorization: Bearer <accessToken>

Refresh tokens rotate on every use - the old one stops working the moment a
new one is issued, and presenting an already-used token again logs everyone
out of that session, not just the one request. This is on purpose: it is what
catches a stolen refresh token being used behind the real user's back.

Public sign-up (POST /auth/register) always creates a patient account, no
matter what the request body says. Doctor and admin accounts are created by
an admin - see the next section - or come from the seed script.

Before deploying anywhere real, generate your own JWT_ACCESS_SECRET - the
placeholder in .env.local is long enough to pass validation for local work,
but the server refuses to start with NODE_ENV=production while it is still in
place:

    node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"

-------------------------------------------------------------------------------
DOCTOR MANAGEMENT AND AVAILABILITY
-------------------------------------------------------------------------------

Everything under /admin/doctors needs an admin's access token. Everything
under /doctors (no /admin prefix) works for any signed-in user - patients
browse the same directory doctors and admins can see.

  Create a doctor, with their first week of shifts in the same request:

    curl -X POST http://localhost:4000/admin/doctors \
      -H "Authorization: Bearer <adminAccessToken>" \
      -H "Content-Type: application/json" \
      -d '{
        "email": "newdoc@clinic.test",
        "password": "a perfectly good passphrase",
        "fullName": "Dr New Comer",
        "specialization": "Pediatrics",
        "workingHours": [
          {"dayOfWeek": 1, "startTime": "09:00", "endTime": "12:00"}
        ]
      }'

  Mark a leave day. This cancels every confirmed appointment already booked
  on it, atomically, and the response says how many:

    curl -X POST http://localhost:4000/admin/doctors/<doctorId>/leaves \
      -H "Authorization: Bearer <adminAccessToken>" \
      -H "Content-Type: application/json" \
      -d '{"leaveDate":"2026-12-25","reason":"Holiday"}'

  A doctor can do the same thing to their own calendar, with no doctor id in
  the URL at all - see DOCTOR PORTAL below.

  See what is actually bookable - the whole point of this module - a real
  live-computed grid, not a static schedule:

    curl "http://localhost:4000/doctors/<doctorId>/availability?from=2026-09-01&to=2026-09-07" \
      -H "Authorization: Bearer <accessToken>"

The availability grid is computed fresh on every call from the doctor's
working hours, minus leave days, minus already-booked appointments, minus
slots someone else currently has on hold - in one database query, in one
round trip. A deactivated doctor (PATCH ... {"isActive": false}) always
returns an empty grid rather than an error - their account and history stay
intact, they are simply not bookable.

Date ranges are capped at 31 days per request (a booking UI never needs more,
and it keeps the query's own work bounded).

-------------------------------------------------------------------------------
BOOKING AN APPOINTMENT
-------------------------------------------------------------------------------

Only a patient account can book. The flow is hold, then confirm - a slot is
reserved for five minutes while the patient fills in the symptom form, then
either turned into a real appointment or left to expire on its own.

  1. Hold a slot. "start" is copied straight from an availability response
     above - never typed or computed by hand, so the client never has to
     think about the doctor's timezone at all:

    curl -X POST http://localhost:4000/appointments/hold \
      -H "Authorization: Bearer <patientAccessToken>" \
      -H "Content-Type: application/json" \
      -d '{"doctorId":"<doctorId>","start":"2026-09-01T03:30:00.000Z"}'

     Returns a holdId and an expiresAt five minutes out. A slot someone else
     already holds, or one outside the doctor's real schedule, comes back as
     409 SLOT_UNAVAILABLE rather than a confusing error.

  2. Confirm it with the symptom form:

    curl -X POST http://localhost:4000/appointments/<holdId>/confirm \
      -H "Authorization: Bearer <patientAccessToken>" \
      -H "Content-Type: application/json" \
      -d '{"symptoms":"Persistent headache for three days, worse in the mornings."}'

     Returns the booked appointment. The hold is gone the instant this
     succeeds, and confirming it a second time - a doubled network request,
     say - correctly 404s rather than booking twice.

  3. See your own bookings, or cancel one:

    curl http://localhost:4000/appointments/mine \
      -H "Authorization: Bearer <patientAccessToken>"

    curl -X DELETE http://localhost:4000/appointments/<appointmentId> \
      -H "Authorization: Bearer <patientAccessToken>" \
      -H "Content-Type: application/json" \
      -d '{"reason":"Feeling better, no longer needed"}'

     Cancelling frees the slot immediately - it shows up in the availability
     grid again right away. An admin can also fetch or cancel any patient's
     appointment (a normal support action). The assigned doctor can also read
     it - see DOCTOR PORTAL below for their own schedule view.

-------------------------------------------------------------------------------
DOCTOR PORTAL
-------------------------------------------------------------------------------

Everything here is doctor-only, and none of it takes a doctor id anywhere in
the request - the API always reads who is asking from the access token, the
same way a patient's own /appointments/mine never takes a patient id either.

  A doctor's own day (or up to a 31-day range), sorted by visit time:

    curl "http://localhost:4000/appointments/schedule?from=2026-09-01&to=2026-09-01" \
      -H "Authorization: Bearer <doctorAccessToken>"

  Complete a visit - notes plus a structured prescription. This is what
  fires the post-visit AI summary (Phase 6) and schedules medication
  reminders (Phase 8):

    curl -X POST http://localhost:4000/appointments/<appointmentId>/notes \
      -H "Authorization: Bearer <doctorAccessToken>" \
      -H "Content-Type: application/json" \
      -d '{
        "doctorNotes": "Mild seasonal allergy. Advised rest and fluids.",
        "prescription": [
          {"drug":"Cetirizine","dosage":"10mg","timesPerDay":1,"durationDays":5}
        ]
      }'

  Self-service leave management - list, preview, mark, and remove a day off
  on the caller's own calendar:

    curl http://localhost:4000/doctors/me/leaves \
      -H "Authorization: Bearer <doctorAccessToken>"

    curl "http://localhost:4000/doctors/me/leaves/preview?leaveDate=2026-12-25" \
      -H "Authorization: Bearer <doctorAccessToken>"

     Returns {"affectedAppointments": N} - a real, read-only count of what
     marking that day would cancel, computed before anything is committed.
     The browser app shows this as a warning with a separate confirm step.

    curl -X POST http://localhost:4000/doctors/me/leaves \
      -H "Authorization: Bearer <doctorAccessToken>" \
      -H "Content-Type: application/json" \
      -d '{"leaveDate":"2026-12-25","reason":"Personal leave"}'

    curl -X DELETE http://localhost:4000/doctors/me/leaves/<leaveId> \
      -H "Authorization: Bearer <doctorAccessToken>"

-------------------------------------------------------------------------------
ADMIN PORTAL
-------------------------------------------------------------------------------

Everything here needs an admin's access token.

  The full doctor roster - active and deactivated alike, unlike the
  patient-facing GET /doctors above, which always hides a deactivated one:

    curl http://localhost:4000/admin/doctors \
      -H "Authorization: Bearer <adminAccessToken>"

  Preview a leave day's impact on any doctor's calendar before marking it -
  the same read-only count a doctor gets over their own days off in
  DOCTOR PORTAL above, here for an admin managing someone else's:

    curl "http://localhost:4000/admin/doctors/<doctorId>/leaves/preview?leaveDate=2026-12-25" \
      -H "Authorization: Bearer <adminAccessToken>"

  Notification Health - a count per status, then the same dead-letter list
  and retry from EMAIL NOTIFICATIONS below:

    curl http://localhost:4000/admin/notifications/summary \
      -H "Authorization: Bearer <adminAccessToken>"

  The audit log - every action `shared/audit.ts` has recorded since Phase 2,
  newest first, with the actor's name joined in:

    curl http://localhost:4000/admin/audit-log \
      -H "Authorization: Bearer <adminAccessToken>"

    curl "http://localhost:4000/admin/audit-log?action=appointment_cancelled&page=1&pageSize=25" \
      -H "Authorization: Bearer <adminAccessToken>"

-------------------------------------------------------------------------------
EMAIL NOTIFICATIONS
-------------------------------------------------------------------------------

Booking, cancelling, and the reminder scheduler all queue a row in
notification_outbox rather than sending anything directly - the
transactional outbox pattern, so a crash right after a booking commits can
never lose the confirmation email. A background job drains that table every
20 seconds.

With no BREVO_API_KEY set (see .env.local), emails are printed to this
process's own log instead of sent - a completely normal way to run and demo
the whole project. Book an appointment, then watch the API's terminal output
for a line like:

    Email sender not configured - printing instead of sending

That is the confirmation email, in full, right there in the log. Set
BREVO_API_KEY, BREVO_SENDER_EMAIL and BREVO_SENDER_NAME to send real email
through Brevo's free tier (300/day, forever, no card) instead.

Reminders queue themselves automatically: a background tick every five
minutes looks for confirmed appointments starting within the next 24 hours,
and separately within the next hour, and queues one reminder each. Queuing
uses the same idempotency key every time it rediscovers the same
appointment, so running that tick repeatedly is always safe - it can never
send the same reminder twice.

A notification that fails five times in a row - a real account is
misconfigured, say - stops retrying itself and becomes visible to an admin
instead of vanishing:

    curl http://localhost:4000/admin/notifications/dead-letter \
      -H "Authorization: Bearer <adminAccessToken>"

    curl -X POST http://localhost:4000/admin/notifications/<id>/retry \
      -H "Authorization: Bearer <adminAccessToken>"

Retrying gives it a completely fresh set of five attempts, on the
understanding that whatever was wrong has now been fixed.

To watch the raw table directly:

    docker exec -it health-appointment-db psql -U health -d health_appointment \
      -c "SELECT recipient_id, type, status, attempts FROM notification_outbox;"

-------------------------------------------------------------------------------
AI SUMMARIES
-------------------------------------------------------------------------------

Two moments in a visit get an AI-written summary: booking one queues a pre-visit triage brief for
the doctor, and a doctor submitting their notes queues a plain-language summary for the patient.
Both are fired after their own request has already answered - a slow or failing AI call never
makes booking or notes submission feel slow - so the appointment you get back from either call
still shows the previous status for a moment. Fetch the appointment again a second later to see
the finished result.

With no GROQ_API_KEY or GEMINI_API_KEY set (see .env.local), both moments fall back to an honest,
fixed message telling the reader to check the patient's or doctor's own text instead - a
completely normal way to run and demo the whole project. Set either key, or both, to see a real
summary; Groq goes first with one retry, then Gemini, and if both are configured and both happen
to fail, the same fallback message is used.

  Book an appointment as a patient, the same as in the section above, then check on it:

    curl "http://localhost:4000/appointments/<appointmentId>" \
      -H "Authorization: Bearer <patientAccessToken>"

  aiPrevisitStatus moves from "not_requested" to "pending" to either "ready" (a real summary, with
  aiUrgency / aiChiefComplaint / aiSuggestedQuestions filled in) or "unavailable" (the fallback
  message, in aiChiefComplaint). A doctor can fetch the same appointment to read it before the
  visit - this is the one case where GET /appointments/:id works for a doctor at all, since it is
  their own side of the same visit:

    curl "http://localhost:4000/appointments/<appointmentId>" \
      -H "Authorization: Bearer <doctorAccessToken>"

  After the visit, the doctor submits their notes and a prescription. This also moves the
  appointment to "completed" - it is the only thing in the app that does:

    curl -X POST "http://localhost:4000/appointments/<appointmentId>/notes" \
      -H "Authorization: Bearer <doctorAccessToken>" \
      -H "Content-Type: application/json" \
      -d '{
        "doctorNotes": "Mild seasonal allergy. Advised rest and fluids.",
        "prescription": [
          {"drug": "Cetirizine", "dosage": "10mg", "timesPerDay": 1, "durationDays": 5}
        ]
      }'

  A moment later, aiPostvisitStatus reaches "ready" or "unavailable" the same way, with
  aiPostvisitSummary and aiPostvisitSteps filled in on success. The AI is never asked to restate
  the prescription itself - the doctor's own prescription field is already the exact, correct
  source for drug names and doses, so asking a model to repeat them back would only add a chance
  of it getting one wrong.

  Every attempt - which provider, how long it took, and whether it worked - is written to the
  audit log, including the case where neither key is configured at all:

    docker exec -it health-appointment-db psql -U health -d health_appointment \
      -c "SELECT action, metadata FROM audit_log WHERE action LIKE '%summary_attempt%';"

-------------------------------------------------------------------------------
GOOGLE CALENDAR SYNC
-------------------------------------------------------------------------------

Booking an appointment queues an event for both sides' own Google Calendar; cancelling queues its
deletion. Both travel through the same notification_outbox every email already uses, just on
channel='calendar' instead of channel='email' - a slow or failed Google call can never delay a
booking response, for exactly the same reason a slow email send cannot.

With none of the four GOOGLE_* variables set (see .env.local), every appointment simply gets no
calendar event, for anyone - not an error, not a retry, not a log line. That is the real, fully
supported way this project runs today, since no Google Cloud project has been set up for it yet.

Once configured, a user connects their own calendar with their own access token - patient and
doctor are independent, and a side that never connects just keeps getting no event while
everything else about their appointments works exactly as before:

  curl "http://localhost:4000/auth/google/connect" \
    -H "Authorization: Bearer <accessToken>"

Returns a real Google consent URL - open it in a browser signed into the Google account you added
as a test user, approve access, and Google redirects back to /auth/google/callback, which answers
with a small HTML page rather than JSON, since a real browser tab lands there, not an API client.

  curl "http://localhost:4000/auth/google/status" \
    -H "Authorization: Bearer <accessToken>"

  curl -X POST "http://localhost:4000/auth/google/disconnect" \
    -H "Authorization: Bearer <accessToken>"

Disconnecting deletes the stored, encrypted tokens and makes a best-effort attempt to revoke them
at Google's end too - the local delete is what actually matters, and never waits on that second
call succeeding.

Every stored access and refresh token is encrypted at rest with AES-256-GCM before it ever reaches
the database - GOOGLE_TOKEN_ENCRYPTION_KEY is the only thing that can decrypt them, and it never
leaves this server. A revoked or expired connection is not silently ignored: the next attempt to
sync that person's calendar fails with a clear reason and follows the outbox's normal backoff,
eventually reaching the same dead-letter dashboard as an email that could not be sent.

    curl http://localhost:4000/admin/notifications/dead-letter \
      -H "Authorization: Bearer <adminAccessToken>"

Retrying a dead-lettered calendar row after reconnecting works exactly like retrying an email one.

-------------------------------------------------------------------------------
MEDICATION REMINDERS AND LEAVE DAYS
-------------------------------------------------------------------------------

Submitting doctor's notes with a prescription (see "AI SUMMARIES" above for the notes endpoint
itself) does one more thing: it expands each drug into a full course of reminders, one
row per dose, in medication_reminders. "Three times a day for five days" becomes exactly fifteen
rows, spread across 08:00 / 14:00 / 20:00 each day rather than the full 24 hours, so nobody gets
woken at 3 AM by a naive even split - and every one of those times is computed in the patient's
own timezone, correctly, across a daylight-saving change if the course happens to cross one.

    docker exec -it health-appointment-db psql -U health -d health_appointment \
      -c "SELECT drug_name, scheduled_at FROM medication_reminders WHERE appointment_id = '<id>' ORDER BY scheduled_at;"

A background tick every five minutes looks for reminders whose time has come and queues one
notification_outbox row each - sending itself is left to the same outbox worker every other
notification already goes through, so a medication reminder is just as durable against a crash as
a booking confirmation is. Running the same prescription through twice never creates a second set
of reminders; a unique constraint on the appointment, drug, and exact time makes re-running it a
no-op.

Marking a doctor's leave day cancels whatever is already booked on it, in one transaction with the
leave itself - either both happen or neither does:

    curl -X POST "http://localhost:4000/admin/doctors/<doctorId>/leaves" \
      -H "Authorization: Bearer <adminAccessToken>" \
      -H "Content-Type: application/json" \
      -d '{"leaveDate": "2026-12-25", "reason": "Holiday"}'

The response's cancelledAppointments field says how many patients were affected. Each of them gets
a "needs to be rebooked" email - worded as the doctor's own unavailability, not as something the
patient chose - and both sides' calendars lose the event, the same way any other cancellation's
calendar cleanup works. The doctor does not get an email about their own leave; their calendar
still gets cleaned up.

-------------------------------------------------------------------------------
RUNNING THE TESTS
-------------------------------------------------------------------------------

The tests need Postgres running, because the most important thing they check -
that two patients cannot book the same slot - is enforced by the database
itself. Faking it would only prove the fake agrees with the test.

  npm run db:up
  npm test

The suite creates its own database called health_appointment_test and migrates
it automatically. Your development data is never touched.

There is a second, separate suite for the browser app - a handful of end-to-end
tests that drive a real headless browser through the actual patient journey
(search, hold, confirm, cancel) against the real API and a real database. It
needs both servers already running, which is real infrastructure npm run check
should never have to assume exists, so it stays out of that gate and runs on
its own:

  npm run dev             (terminal 1)
  npm run dev:web         (terminal 2)
  npx playwright install chromium --with-deps   (one time only)
  npm run e2e --workspace @health/web

That one-time install step downloads a headless Chromium build (a few hundred
MB) - Playwright's own test runner will refuse to start and tell you to run it
if you skip this and it is missing.

-------------------------------------------------------------------------------
DEPLOYING TO PRODUCTION
-------------------------------------------------------------------------------

Every piece below is free, permanently, with no credit card - not a trial that
starts asking for one later. Do these in order; each step needs a real URL
the previous one produced.

  1. Database - Neon (https://neon.com)

     Create a project, then copy the POOLED connection string (not the direct
     one - the direct one runs out of connections quickly on a free plan).
     That string is DATABASE_URL for the next step.

  2. API - Render (https://render.com)

     New -> Blueprint -> connect this repo. Render reads render.yaml at the
     repo root and provisions the service on the free plan automatically -
     build command, start command and health check path are all already in
     that file. You will be prompted for the values marked "sync: false" in
     render.yaml: DATABASE_URL from step 1, and anything from the optional
     services above you want turned on now (all of them can be left blank
     and filled in later from the Render dashboard without a redeploy).

     CORS_ORIGINS is also prompted for here but does not have a real answer
     yet - leave it as the placeholder in .env.local (http://localhost:5173)
     for this first deploy. Step 4 below comes back and fixes it once the
     Cloudflare Pages URL actually exists.

     Once deployed, note this service's URL (something like
     https://health-appointment-api.onrender.com) - the browser app needs it
     next.

  3. Web app - Cloudflare Pages (https://pages.cloudflare.com)

     Create a project from this same repo, with these exact settings:

       Root directory:    / (the repo root, not apps/web - this is an npm
                           workspaces monorepo, and npm install has to run
                           at the root for @health/contracts to resolve)
       Build command:     npm install && npm run build --workspace @health/contracts
                           && npm run build --workspace @health/web
       Build output dir:  apps/web/dist

     Environment variables (Production and Preview both):

       VITE_API_URL = the Render URL from step 2

     Deploy, then note this project's own URL (something like
     https://health-appointment.pages.dev).

  4. Close the loop: go back to the Render service from step 2 and set
     CORS_ORIGINS to the Cloudflare Pages URL from step 3 (comma-separate
     more than one origin if you also keep a custom domain). Save - Render
     redeploys automatically. The two services now trust each other.

  5. Keep the free API instance warm - cron-job.org (https://cron-job.org)

     Render's free plan spins a service down after 15 minutes of no traffic,
     and the next request pays a real cold-start cost (the reasoning behind
     the ColdStartNotice component in the browser app). A free cron-job.org
     account pinging https://<your-render-url>/health every 10 minutes keeps
     that from ever happening to a real visitor - /health answers instantly
     and touches no database, so this ping costs nothing and proves nothing
     about whether the database itself is reachable (that is what /ready is
     for, and this ping deliberately does not use it).

  6. Confirm the whole thing for real: open the Cloudflare Pages URL, sign in
     with a seeded demo account (see DEMO LOGINS above - re-run
     `npm run db:seed` against the Neon database first if it is empty), and
     walk through a real booking. Every endpoint documented throughout this
     file works exactly the same against these URLs as it does against
     localhost - only the base URL changes.

A full, live-generated API reference - every route, every request and
response shape, straight from the same Zod schemas each route validates
against - is always available at GET /openapi.json on either the local or
the deployed API. Import that URL directly into Postman (File -> Import ->
Link) to get a complete, always-current request collection with no separate
file to keep in sync by hand.

  apps/api                 The HTTP API and the background scheduler
  apps/api/src/db          Schema, migrations, seed data
  apps/web                 The patient/doctor/admin portals - a Vite + React
                           single-page app, statically hosted
  apps/web/src/lib         The typed API client, the in-memory session, and
                           the TanStack Query client's own retry/stale rules
  apps/web/src/features    Auth actions/hooks and each resource's query hooks
  apps/web/src/routes      One file per page, each its own lazy-loaded chunk
  apps/web/e2e             End-to-end tests driving a real headless browser
  packages/contracts       Zod schemas shared by the API and the browser, so
                           the two can never disagree about a payload shape
  scripts/                 Small build and setup helpers, plain Node
  docs/                    This file
  docker-compose.yml       Local Postgres, matching the version Neon runs
  render.yaml              Render Blueprint for the API - see DEPLOYING TO
                           PRODUCTION above

Migrations are plain .sql files in apps/api/src/db/migrations. They are applied
in filename order and their contents are hashed once applied, so editing one
that has already run is caught instead of silently producing two different
databases. To change the schema, add a new numbered file.
